# 体系的デバッグ

## 概要

当てずっぽうの修正は時間を浪費し、新たなバグを生む。応急パッチは根本問題を覆い隠す。

**核心原則:** 修正の前に必ず根本原因を突き止める。症状への対症療法は失敗である。

**字面の違反は精神の違反である。**

## 鉄則

```
根本原因調査なしに修正しない
```

フェーズ 1 を完了していないなら、修正を提案する資格はない。

## 適用範囲

あらゆる技術的問題: テスト失敗 / バグ / 予期しない挙動 / 性能問題 / ビルド失敗 / 連携不具合。

**特に使うべき場面:**
- **時間圧があるとき**（緊急時ほど当て推量に流れる。体系的アプローチのほうが速い）
- 「ちょっとした修正」が自明に見えるとき
- すでに複数の修正を試したとき / 前の修正が効かなかったとき
- 問題を完全には理解していないとき

「単純な問題だから手順不要」も禁止。単純なバグにも根本原因はあり、単純なら手順も速く終わる。

## フェーズ 0: フィードバックループの構築（理論より先）

**コードを読んで理論を立てる前に**、このバグで赤になる 1 コマンドを作り、**一度実際に実行**して赤を見る。

条件（全て満たすこと）:
- **タイト** — このバグの症状そのものにアサートする（「落ちなければ OK」ではない）
- **赤にできる** — バグがあれば赤、直れば緑
- **決定的** — 毎回同じ判定（フレーキーなら再現率を上げてから: 100 回ループ・並列化・タイミング窓の圧縮）
- **速い** — 分ではなく秒
- **エージェントが単独実行できる** — 人手の操作なしに回せる

grep_analyzer での構築手段（おおよそこの順で試す）: 失敗する pytest（`python -m pytest tests/unit/test_x.py -q --tb=line`）→ 固定入力での CLI 起動と既知良出力との diff → 実データの断片を `tmp_path` 型フィクスチャに切り出して再生 → 新旧 2 構成での差分実行。

どうしても作れなければ**停止して報告**する。試したことを列挙し、再現環境・ログ等の成果物・一時計測の許可を求める。**ループなしで仮説フェーズへ進まない。**

## 4 フェーズ

各フェーズを完了してから次へ進むこと。

### フェーズ 1: 根本原因調査

**いかなる修正の前にも:**

1. **エラーメッセージを精読** — スタックトレースを最後まで読む。行番号・ファイルパス・エラーコードを控える。答えが書いてあることは多い
2. **一貫した再現** — フェーズ 0 のループで確実に赤にできるか。できないならデータ収集を続ける。推測しない
3. **最近の変更を確認** — `git diff` / 直近コミット / 依存・設定・環境の差分
4. **多層システムでは証拠を集める** — 各コンポーネント境界で「入るデータ / 出るデータ / 設定の伝播」を記録し、**どの層で壊れるか**を証拠で特定してからその層を調べる（例: CLI 引数解析 → 走査 → 分類 → TSV 出力 の各境界に計測を仕込む）
5. **データフローを遡る** — 不正な値の発生源はどこか。悪い値で呼んだのは誰か。発生源まで遡って**源で直す**。症状の場所で直さない

**計測用の仕込みコードには一意タグを付ける**（例: `print(f"[DEBUG-a4f2] enc={enc}")`）。撤去は `grep -rn "DEBUG-a4f2"` の一発になる。タグなしのログは生き残り、タグ付きのログは死ぬ。

### フェーズ 2: パターン分析

1. **動いている類例を探す** — 同一コードベース内の似た正常コードはどこか
2. **参照実装は完全に読む** — 流し読み禁止。パターンを理解してから適用する
3. **差分を列挙する** — 動く方と壊れた方の違いを、どんな些細なものも列挙。「それは関係ないはず」と決めつけない
4. **依存を理解する** — 必要な設定・環境・前提は何か

### フェーズ 3: 仮説と検証

1. **仮説を 3〜5 個、反証可能な形で出しランク付けする** — 最初の思いつき 1 個に錨を下ろさない。各仮説は「もし X が原因なら、Y を変えればバグは消える／Z を変えれば悪化する」の形で予測を明記。予測を書けない仮説は雰囲気であり、捨てるか研ぎ直す
2. **最小で検証** — 仮説を試す最小の変更。一度に 1 変数のみ。複数同時に直さない
3. **確認してから進む** — 当たり → フェーズ 4。外れ → 新しい仮説。**外れの上に修正を積まない**
4. **分からないときは言う** — 「X を理解していない」と明言し、調べるか人間のパートナーに聞く。知ったかぶりをしない

### フェーズ 4: 実装

1. **失敗する再現テストを先に作る** — 最小の再現。修正の前に必ず用意する。書き方は `test-driven-development` スキルに従う（赤の確認必須）
2. **単一の修正** — 特定した根本原因だけを直す。一度に 1 変更。「ついで」の改善・リファクタリング同梱は禁止
3. **修正を検証** — 再現テストが緑になり、`python -m pytest tests/ -q --tb=line` で他が壊れていないこと（完了宣言は `verification-before-completion` に従う）
4. **効かなかったら停止** — 試した修正の回数を数える。3 回未満 → 新情報を持ってフェーズ 1 へ戻る。**3 回以上 → 停止してアーキテクチャを疑う**

### 修正 3 連敗 = アーキテクチャ問題

兆候: 修正のたびに別の場所で新たな共有状態・結合・症状が露出する / 修正に「大規模改修」が必要になる。

これは仮説の外れではなく、**設計が間違っている**。問い直す:
- このパターンはそもそも健全か？ 惰性で維持していないか？
- 症状の修正を続けるより設計を改めるべきでは？

**4 回目の修正を試みる前に、人間のパートナーと議論する。**

## レッドフラグ — 停止してフェーズ 1 へ

- 「とりあえず直して、調査は後で」
- 「X を変えてみて様子を見よう」
- 「複数まとめて変えてテストしよう」
- 「テストは省いて手で確認する」
- 「たぶん X だろう、直してみる」
- 「完全には理解してないがこれで動くかも」
- 調査なしに修正リストを列挙している / データフローを追う前に解決策を提案している
- ループ（フェーズ 0）が無いままコードを読んで理論を組み立てている
- **「もう 1 回だけ修正を」（既に 2 回以上失敗）** / **修正のたびに別の場所で新問題**

## 合理化への反駁テーブル

| 言い訳 | 現実 |
|--------|------|
| 「単純な問題だから手順不要」 | 単純なバグにも根本原因がある。手順は単純なら速い |
| 「緊急事態、手順の時間がない」 | 体系的デバッグは当て推量の乱打より**速い** |
| 「まずこれを試して、駄目なら調査」 | 最初の一手が型を決める。最初から正しくやる |
| 「修正が効いたのを確認してからテストを書く」 | テスト無しの修正は定着しない。先に赤で証明する |
| 「まとめて直せば時間短縮」 | どれが効いたか分離できず、新バグを生む |
| 「参照が長いので要点だけ流用」 | 部分理解はバグを保証する。完全に読む |
| 「問題は見えている、直させてくれ」 | 症状が見える ≠ 根本原因を理解している |
| 「もう 1 回だけ」（2 回以上失敗後） | 3 連敗 = 設計問題。修正でなくパターンを疑う |

## 調査しても根本原因が「無い」とき

真に環境・タイミング・外部要因だと判明したら: 調査内容を記録し、適切な処置（リトライ・タイムアウト・エラーメッセージ）と将来のための計測を実装する。ただし**「根本原因なし」の 95% は調査不足**である。
