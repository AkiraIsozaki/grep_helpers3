# コードレビューの受け方

コードレビューに必要なのは技術的評価であって、感情のパフォーマンスではない。

**基本原則:** 実装の前に検証する。推測の前に質問する。社交的な心地よさより技術的正しさ。

## 応答パターン

```
レビューフィードバックを受けたら:
1. READ: 反応せずに全文を読む
2. UNDERSTAND: 要求を自分の言葉で言い直す（できなければ質問する）
3. VERIFY: コードベースの実態と照合して検証する
4. EVALUATE: 「この」コードベースにとって技術的に妥当か評価する
5. RESPOND: 技術的な応答、または根拠ある反論
6. IMPLEMENT: 1件ずつ実装し、都度テストする
```

## 禁止応答

**決して言わないこと:**
- 「おっしゃる通りです!」（明示的な指示違反）
- 「良い指摘!」「素晴らしいフィードバック!」（迎合）
- 「ありがとうございます」等、あらゆる感謝表現
- 検証前の「では実装します」

**代わりに:** 技術的要求を言い直す / 明確化の質問をする / 間違っていれば技術的根拠で反論する / 黙って作業を始める（言葉より行動）。

**「Thanks」と書きそうになったら:** 削除して、修正内容を述べる。コード自体がフィードバックを聞いた証拠になる。

## 不明瞭なフィードバックの扱い

```
1件でも不明瞭な項目があれば:
  停止 — まだ何も実装しない
  不明瞭な項目の明確化を求める
理由: 項目同士は関連しうる。部分的な理解 = 誤った実装。
```

**例:** 「1〜6を直して」と言われ、1,2,3,6 は理解、4,5 が不明。
- ❌ 1,2,3,6 を先に実装し、4,5 は後で聞く
- ✅ 「1,2,3,6 は理解した。着手前に 4 と 5 の明確化が必要」

## 出所別の扱い

**パートナー（人間）から:** 信頼する — 理解したら実装する。ただし範囲が不明瞭なら質問する。迎合的同意はしない。

**外部レビュアーから:** 懐疑的に、ただし丁寧に検証する。
```
実装前に確認:
  1. このコードベースにとって技術的に正しいか
  2. 既存機能を壊さないか
  3. 現行実装にはそうなっている理由があるか
  4. 全プラットフォーム・バージョンで動くか
  5. レビュアーは文脈を全部把握しているか

提案が誤りに見える → 技術的根拠で反論
容易に検証できない → 「[X] なしでは検証できない。調査/確認/続行のどれにするか」と述べる
パートナーの過去の決定と矛盾 → 停止してパートナーとまず相談
```

## 「ちゃんと実装して」系への YAGNI チェック

```
レビュアーが「本格的に実装すべき」と提案したら:
  コードベースを grep して実際の使用箇所を探す
  未使用 → 「このエンドポイントは呼ばれていない。削除では (YAGNI)?」
  使用中 → 本格的に実装する
```

## 実装順序

```
複数項目のフィードバック:
  1. まず不明点をすべて解消する
  2. 実装順: ブロッカー（破壊・セキュリティ）→ 単純修正（typo・import）→ 複雑修正（リファクタ・ロジック）
  3. 1件ずつ修正し、都度 python -m pytest tests/ -q --tb=line で確認
  4. リグレッションがないことを確認
```

## 反論すべきとき

- 提案が既存機能を壊す / レビュアーに文脈が欠けている
- YAGNI 違反（未使用機能）/ このスタックでは技術的に不正確
- 互換性・レガシー上の理由がある / パートナーの設計判断と矛盾する

**反論の仕方:** 防衛でなく技術的根拠で。具体的に質問する。動いているテスト・コードを参照する。設計に関わるならパートナーを巻き込む。

## 正しい指摘への応答

```
✅ 「修正した。[変更内容の簡潔な説明]」
✅ 「[具体的な問題] を確認。[場所] で修正済み」
✅ [黙って直してコードで示す]
❌ 感謝・賞賛のいかなる表現
```

## 自分の反論が間違っていたとき

事実のみを一行で述べて先へ進む。長い謝罪・反論した理由の弁明・過剰な説明はしない。
```
✅ 「確認した。[X] は確かに [Y] だった。修正する」
```

## よくある失敗

| 失敗 | 修正 |
|------|------|
| 迎合的同意 | 要求を言い直すか、黙って行動 |
| 盲目的実装 | まずコードベースと照合 |
| まとめて実装しテスト省略 | 1件ずつ、都度テスト |
| レビュアーは正しいと仮定 | 壊れないか確認 |
| 反論の回避 | 心地よさより技術的正しさ |
| 部分実装 | 先に全項目を明確化 |
| 検証できないまま続行 | 限界を述べて指示を仰ぐ |

## 結論

**外部フィードバック = 評価すべき提案であり、従うべき命令ではない。**

検証し、質問し、それから実装する。迎合的同意はしない。常に技術的厳密さを。
