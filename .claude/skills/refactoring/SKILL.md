# Python リファクタリングスキル

このスキルは、**ソースコードとドキュメントの完全な整合性**を保ちながら、
保守性・拡張性・設計品質を向上させる `grep_analyzer`（Python 3.12 CLI ツール）の
リファクタリングを実施します。

表面的なコード修正で終わらせず、設計の意図をドキュメントに反映させることが核心です。
**1つのタスクを完了したら、対応するドキュメント更新もその場で行います**（後回しにしない）。

リファクタリングは**挙動を変えません**。テストの入出力（TSV 出力・診断・終了コード）は
前後で一致していなければなりません。挙動を変える必要があるなら、それはリファクタリングではなく
機能変更なので `test-driven-development` スキルで別作業として扱います。

---

## フェーズ0: 準備（必ず最初に実施）

### 既存ドキュメントを読む

```
Read('docs/superpowers/specs/')   # 対象領域の設計文書（refactor-design 等）
Read('docs/PERFORMANCE.md')       # 性能特性に触れる場合
Read('.claude/skills/coding-conventions.md')  # 命名・構造規約
```

これらはプロジェクトの「北極星」です。リファクタリングはこれらの文書が定める
層分離・命名規則・実装原則の範囲内で行います。

### ステアリングファイルを作成

`steering` スキルを使い、`.steering/YYYYMMDD-refactor-<対象>/` に3ファイル
（requirements.md / design.md / tasklist.md）を作成します。

tasklist.md には以下を含めること：

- 分析結果（現状の問題点リスト、または「変更不要」の結論）
- ソース修正タスク（ファイル単位）— 変更がない場合はその旨を記録
- 各タスクに対応するドキュメント更新（タスクと1対1で対応付ける）
- 検証タスク（`python -m pytest tests/ -q --tb=line`）

## フェーズ1: 分析（何が問題かを明確にする）

対象コードを読み、以下の9つの観点で問題を洗い出します。
詳細なパターンと判断基準は `references/python-patterns.md` を参照してください。

**分析の結果、変更が不要な場合も正当な結論です。** その場合は理由を tasklist.md に記録し、
フェーズ2の実装をスキップしてフェーズ4（検証）に進みます。

### 観点1: 関心の分離と可視性

**問いかけ**: 「この名前は本当にモジュール外から見える必要があるか？」

- Python の非公開は規約ベース: モジュール内でしか使わない関数・定数・クラスには `_` 接頭辞
- 公開 API を持つモジュールでは `__all__` で公開面を宣言できないか
- パッケージ境界（`patterns/` `classifiers/` `snippet/` `fixedpoint/`）の外へ露出する名前を最小化する
- **必ず Grep で他モジュールからの使用箇所を確認してから変更する**
- 層分離違反がないか: `patterns/*` は葉（何にも依存しない）、下位が `pipeline`/`cli` を import しない

**既存規約との整合（重要）**: `coding-conventions` の通り、
**モジュールを跨いで共有される helper は public 名のまま**にします。
`_` 接頭辞は「そのモジュール内 private」の宣言なので、他モジュールから import される名前に
付けてはいけません。`_` を外すと壊れる依存が本当に無いものだけが private 化の対象です。

### 観点2: 不変性

**問いかけ**: 「このオブジェクトは生成後に状態が変わるか？変わる必要があるか？」

- 生成後に変更されないデータ構造 → `@dataclass(frozen=True)` にできないか
- 変更されない list → `tuple` に、変更されないモジュール定数 → `Final` 注釈
- 状態更新が必要な frozen dataclass は `dataclasses.replace()` で新インスタンスを生成
- 可変デフォルト引数（`def f(xs: list = [])`）は不変性以前にバグの温床

**なぜ重要か**: 不変オブジェクトは multiprocessing で安全に受け渡せ、テストが簡単で、
「いつ誰が書き換えたか」の追跡が不要になる。

### 観点3: プリミティブ執着

**問いかけ**: 「この str/int は、ドメイン上の意味を持つ概念か？」

- 意味の異なる str が混在（`relpath` と `abspath` 等）→ `NewType` で型レベルに区別を持ち込めないか
- 文字列リテラルの閉じた集合で状態・区分を表現 → `Enum`（`StrEnum`）にできないか
- `tuple[str, int, str]` のような型なし組 → 小さな `dataclass` に包む
- 意味の異なる None が混在する戻り値 → 状態を表す型（dataclass のタグ付き union）で表現

**型の選択指針**:
- **ランタイムコスト無しの区別だけなら `NewType` を優先**
- 複数フィールド・検証（`__post_init__`）が必要なら `dataclass(frozen=True)`
- 閉じた区分の集合なら `Enum`

**注意**: ドメイン語彙の表記（`relpath` / `lineno` / `symbol` 等）は `coding-conventions` で
固定されている。新しい型を導入しても語彙の表記は変えない。

### 観点4: 名前設計

命名の判断基準（フルスペル原則・略語ホワイトリスト・述語 `is_*`/`has_*`/`should_*`・
ドメイン語彙の表記固定・rename 除外規則）は **`coding-conventions` スキルに全て定義済み**です。
このスキルでは重複記述しません。分析時は `coding-conventions` を読み込み、
その規約への違反を問題点として列挙してください。

### 観点5: インターフェース（Protocol / ABC）

**問いかけ**: 「この依存は具象クラスに対してか、抽象に対してか？」

- テスト時に差し替えたい処理（ファイル I/O、外部プロセス起動等）が具象実装に直接依存していないか
- Python では **構造的部分型の `typing.Protocol` を第一候補**にする（既存クラスを変更せず適合できる）
- 明示的な継承階層と共通実装が必要な場合のみ `abc.ABC`
- **過度な抽象化は避ける**。実装が2つ以上存在するか、テスタビリティのために必要な場合のみ導入

### 観点6: ドキュメントとの乖離

**問いかけ**: 「このモジュールの責務は docs/ の設計文書と一致しているか？」

- `docs/superpowers/specs/` の設計文書に書かれた構成・責務と実装がずれていないか
- 層分離ルール（葉→根の一方向、循環禁止）に違反していないか
- 性能に関わる変更なら `docs/PERFORMANCE.md` の記述と矛盾しないか
- モジュール docstring（責務1〜2行 + `Related: spec §X`）が実態と合っているか

### 観点7: 重複コードの抽出

**問いかけ**: 「このコードブロック、別の場所でも見たことがあるか？」

- 同じ構造の try-except + 診断記録が複数関数に出現 → 高階関数か contextmanager に抽出
- 似た条件分岐の連鎖が複数箇所 → 分岐表（dict）や `match` 文への集約を検討

**判断基準は `coding-conventions` の「DRY 誤適用防止」と同一**:
Rule of Three（3箇所目が出てから抽象化）に加え、集約前に
(1) 同一知識か（片方だけ変わるシナリオが想像できるなら寄せない）、
(2) 同じ用語で説明できるか、を必ず確認する。
「偶然2箇所が同じ形」を安易に寄せないこと。

### 観点8: 関数の長さと複雑度

**問いかけ**: 「この関数は1つのことをしているか？テスト時に1行で説明できるか？」

- **20行を超える関数** → 意図を表す名前の `_` 接頭辞関数への抽出を検討
- **ネストが2段以上の if/for** → 早期 return または抽出された関数で平坦化
- **関数名に `and` / `then` が入る** → 複数の責務を担っているサイン

**目安**: 関数本体 20〜30 行以内、1モジュール 300 行以内
（超えたら `snippet/` や `fixedpoint/` のように責務別サブパッケージ化を検討）。

### 観点9: エラー処理の設計

**問いかけ**: 「このエラー処理は必要最小限の粒度か？同じパターンが一貫しているか？」

- **`except Exception:` や裸の `except:`** → 本当に捕捉すべき例外型に絞る
- **握りつぶし（`except ...: pass`）禁止** → 最低でも diagnostics に記録するか、上位へ伝播させる
- **同類の関数で捕捉する例外型・失敗の表現がバラバラ** → 一貫したエラーポリシーに統一
- **失敗を None で返している** → 理由が伝わらない。例外を送出するか、失敗理由を持つ結果型にする
- **例外の変換時は `raise ... from e`** で原因の連鎖を保つ

### 追加観点: 深いモジュール（codebase-design の語彙）

上記9観点を横断する補助レンズとして、次の3つの問いを分析に加えます。

- **深いモジュールか**: 小さいインターフェースの背後に大きい実装が隠れているか。
  インターフェースが実装と同じくらい複雑な「浅いモジュール」は統合候補。
- **削除テスト**: このモジュールを消して呼び出し側に中身を展開したら複雑さは増えるか？
  増えないなら単なる通過点（pass-through）であり、存在意義を疑う。
- **依存は受け取る・結果は返す**: 関数内部で依存を生成したり引数を破壊的に変更したりせず、
  依存は引数で受け取り、結果は戻り値で返す。テスト容易性が上がる。

これらは既存の層分離・可視性規約と矛盾しない範囲で適用します（優先度は9観点より低い）。

## フェーズ2: 実装とドキュメント更新（1タスク = コード + ドキュメント）

### 実装の順序（依存関係を考慮）

1. **葉のモジュールから始める**（`patterns/*` など依存されない側）— 依存する側が先に安定する
2. **Protocol / 型定義** — 実装変更前に契約を確定させる
3. **NewType / dataclass の導入** — プリミティブを包む新型の追加（既存型の変更前に）
4. **可視性の絞り込み** — public → `_` 接頭辞への変更（Grep で使用箇所確認後）
5. **根に向かって修正**（classifiers → pipeline → cli の順）

### 各タスクの完了サイクル（これを繰り返す）

```
① コードを変更する
② python -m pytest tests/ -q --tb=line でグリーンを確認（失敗したら即修正）
③ このタスクに対応するドキュメントを更新する（後回しにしない）
④ tasklist.md の該当タスクを [x] に更新する
⑤ 次のタスクへ
```

**ドキュメントをその場で更新する理由**: 実装の最後にまとめて更新しようとすると、
コンテキストが足りなくなった場合にドキュメント更新がスキップされます。
1タスクが終わるたびに対応するドキュメントも完結させることで、
部分的な状態でも「実装とドキュメントが常に一致している」を保証します。

テストを新規追加・修正する場合は `writing-tests` スキルの規約に従います。

### タスクに対応するドキュメント更新の早見表

| 変更の種類 | 更新するドキュメント |
|-----------|----------------------|
| 新しい型（NewType / dataclass / Enum）の追加 | `docs/superpowers/specs/` の該当設計文書 |
| モジュール分割・サブパッケージ化 | 設計文書の構成記述、README.md（構成に触れていれば） |
| 可視性ルール・命名判断の一般化 | `.claude/skills/coding-conventions.md`（規約へ追記） |
| 重複コードの共通 helper 抽出 | 設計文書（helper の置き場所と責務） |
| エラー処理方針の統一 | 設計文書（エラーポリシーの記述） |
| 性能特性に影響しうる変更 | `docs/PERFORMANCE.md` |
| モジュールの責務変更 | 当該モジュールの docstring + 設計文書 |

### 実装パターン（コードスニペット）

**可視性の絞り込み**:
```python
# Before: モジュール内でしか使われないのに public
def normalize_span(span: tuple[int, int]) -> tuple[int, int]: ...

# After: モジュール内 private（他モジュールからの import が無いことを Grep で確認済み）
def _normalize_span(span: tuple[int, int]) -> tuple[int, int]: ...
```

**不変な値オブジェクト**:
```python
@dataclass(frozen=True)
class Occurrence:
    """1つのキーワード出現位置。生成後は変更しない。"""
    relpath: str
    lineno: int
    symbol: str
```

詳細なパターン・アンチパターンは `references/python-patterns.md` を参照してください。

## フェーズ3: 最終整合確認

全タスクの実装とドキュメント更新が終わったら、全体を俯瞰して確認します。

- tasklist.md の全タスクが `[x]` になっているか
- 変更に対応するドキュメントが全て更新されているか（早見表と照合）
- 古くなった記述（旧関数名・旧モジュール名・旧構成）がドキュメントに残っていないか
- 変更したモジュールの docstring が新しい責務を正しく述べているか

## フェーズ4: 検証

```bash
python -m pytest tests/ -q --tb=line   # 全テストグリーン
```

このプロジェクトにリンタは無いため、テストが唯一のゲートです。
失敗した場合はフェーズ2に戻って修正します。

完了宣言の前に `verification-before-completion` スキルの手順で
「証拠を見てから完了と言う」ことを徹底してください。

## フェーズ5: 振り返り

`steering` スキルの振り返りモードを使い、tasklist.md に記録：

- 実施した変更の概要（「変更なし」の場合はその理由）
- 計画と実績の差分（計画になかった変更や、やめた変更）
- 次回のリファクタリングへの示唆

---

## 重要な判断基準

### 「変更なし」も正当な完了

分析の結果、変更が不要だった場合は：

- tasklist.md に「変更対象なし」と理由を記録する
- フェーズ4（検証）でテストが通ることを確認する
- フェーズ5（振り返り）で分析の結果を記録する

これはリファクタリングの失敗ではなく、**現在の設計が適切であるという確認**です。

### やりすぎないために

- 依頼範囲外のモジュールの変更（スコープを守る）
- 将来の要件を先取りした抽象化（YAGNI: You Aren't Gonna Need It）
- 挙動を変えること（リファクタリングは動作を変えない。出力・診断・終了コードは前後で一致）
- すべての名前に `_` を付けること（公開 API とモジュール跨ぎ helper は public のまま）

### 迷ったときの問いかけ

「この変更で、**次にここを修正する人**の仕事が楽になるか？」

答えが Yes なら変える。No なら変えない。
