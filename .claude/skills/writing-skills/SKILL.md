# スキル執筆

## このプロジェクトの前提

- スキル置き場: `/workspaces/grep_helpers3/.claude/skills/<name>/SKILL.md`(1スキル=1ディレクトリ)
- 全スキルは日本語で書く
- frontmatter は `name` と `description` のみ(他フィールド禁止)
- 他スキルへの参照はプレーン名のみ(例: `test-driven-development`)。接頭辞・`@` リンク禁止

## 概要

**スキル執筆とは、プロセス文書に対する TDD である。**

スキルは確率的なシステムから決定性を絞り出すために存在する。根本の美徳は**プロセスの予測可能性**——毎回同じ出力ではなく、毎回同じ手順をエージェントが踏むこと。以下の全ての手法はこの一点に奉仕する。

**必須背景:** `test-driven-development` の RED-GREEN-REFACTOR サイクルを理解していること。本スキルはそれを文書に適用する。

## 鉄則

```
失敗するテストなしにスキルを書かない
```

新規作成にも**既存スキルの編集にも**適用される。スキル無しでエージェントが失敗する様子を見ていないなら、そのスキルが正しいことを教えるかどうか分からない。

**字面の違反は精神の違反である。**「精神は守っている」という言い訳のクラスを丸ごと切り落とすため、この原則を早期に明記する。

**例外なし:**
- 「単純な追記だから」は不可
- 「一節を足すだけだから」は不可
- 「文書の更新にすぎないから」は不可
- テスト前に書いたスキルは削除してやり直す。「参考として残す」も不可。削除は削除

## RED-GREEN-REFACTOR

| TDD | スキル執筆 |
|---|---|
| テストケース | サブエージェントへの圧力シナリオ |
| RED(失敗を見る) | スキル無しで実行し、違反時の**合理化の言い回しを逐語で記録** |
| GREEN(最小コード) | その合理化に**ちょうど**対処する最小スキル。仮想ケース向けの追記はしない |
| リファクタ | 新たな合理化(抜け穴)に明示的カウンターを足し、再テスト |

規律系スキルは複数の圧力(時間・サンクコスト・権威・疲労)を組み合わせてテストし、最大圧力下でも従うことを合格基準とする。

## description の書き方

**description は「いつ使うか」であり「何をするか」ではない。**

処理内容やワークフローを要約すると、エージェントが description だけを読んで本文をスキップする事故が起きる(実測: 「タスク間でコードレビュー」と要約した結果、本文のフローチャートが定める2段階レビューが1回に減った。トリガー条件だけに直すと本文が読まれ、正しく2回行われた)。

- 三人称で書く(システムプロンプトに注入される)
- 「〜のときに使用」で始め、具体的な症状・状況・文脈を列挙する
- 500字以内を目安に。description は毎ターン読み込まれるコンテキスト負荷なので、本文以上に刈り込む
- 同じ分岐の言い換え(類義語トリガーの羅列)は重複。本当に異なる分岐だけ残す
- 規律系なら「違反しかけている症状」もトリガーに含める

```yaml
# 悪い: ワークフローを要約している
description: TDD 用 - まずテストを書き、失敗を見て、最小実装し、リファクタする
# 良い: トリガー条件のみ
description: 機能追加やバグ修正の実装コードを書き始める前に使用
```

## 失敗の型に形式を合わせる

ベースライン(RED)で観察した失敗を分類してから書く。ある失敗型を防ぐ形式は、別の失敗型では裏目に出る。

| ベースラインの失敗 | 正しい形式 | 誤った形式 |
|---|---|---|
| 規則を知りつつ圧力下でスキップ | 禁止 + 合理化テーブル + レッドフラグ | 弱い推奨(「なるべく」「検討する」) |
| 従うが出力の形が誤り | ポジティブなレシピ: 出力が**何であるか**(構成要素と順序)を記す | 禁止の列挙(「〜を書き直すな」) |
| 必須要素の欠落 | テンプレートに REQUIRED スロットを構造として埋め込む | テンプレ近傍の散文注意書き |
| 条件で振る舞いを変えるべき | 観測可能な述語での条件(「ブリーフが存在すれば参照」) | 無条件の規則 + 免除条項 |

**禁止形が形状問題で裏目に出る理由:** 競合するインセンティブ下でエージェントは「〜するな」と交渉を始める。レシピには交渉の余地がない——出力は宣言された形に一致するか、しないかだ。

**形式共通のルール:**
- **ニュアンス条項を書かない。**「重要でなければ X しない」は交渉を再開させる。勝っていたレシピに1つ足しただけで結果がノイズ化した実測がある。真の例外は観測可能な述語による独立した条件として書く
- **免除条項はスコープしない。**「この制限はコードブロックには適用しない」と書いてもコードブロックは抑制される。例外が必要なら規則が届かない構造に作り直す
- **否定形は裏目に出る。**「象を考えるな」は象を想起させる。目標挙動を肯定形で述べ、禁止語を口にしない。肯定形にできない硬いガードレールに限り禁止を残し、必ず代替行動を併記する

## 情報階層と漸進的開示

スキルの内容は**ステップ**(順序ある行動)と**参照**(規則・定義・事実)の2種。どちらを階層のどこに置くかが核心の判断:

1. **スキル内ステップ** — SKILL.md 内の順序ある行動。**各ステップは検証可能な完了基準で終える**(完了/未完了をエージェント自身が判定でき、必要なら網羅的——「変更した全モデルを確認済み」であって「変更リストを作る」ではない)。曖昧な基準は早すぎる完了を招く
2. **スキル内参照** — SKILL.md 内で随時参照される規則群。フラットな同格集合でも構わない
3. **外部参照ファイル** — SKILL.md から押し出した別ファイル。ポインタが発火したときだけ読み込まれる。ポインタの**文言**が到達の確実性を決める

上に置きすぎれば冒頭が肥大し、下に押しすぎれば必要な材料が隠れる。分岐が最良の判定基準: **全分岐が必要とするものはインライン、一部の分岐しか届かないものはポインタの先へ。**

**同居配置:** ある概念の定義・規則・注意点は1つの見出しの下にまとめ、散在させない。一部を読めば近傍が一緒に付いてくる。

**モデル起動 vs ユーザー起動:** description はモデルが自律起動するための索引で、毎ターンのコンテキスト負荷を払う。手動起動しかしないスキルは負荷ゼロだが、ユーザー自身が存在を覚える認知負荷を払う。本プロジェクトの frontmatter は name/description のみなので全スキルがモデル起動——だからこそ description の刈り込みが効く。

## リーディングワード

事前学習に既に存在する圧縮された概念(tight, red, tracer bullet 等)を選び、本文で繰り返して分散した定義を蓄積させる。最少トークンで挙動の一領域を係留できる。

- 「高速で決定的で低オーバーヘッドな」→ **tight**(タイトなループ)
- 「信じられるループ」→ **red**(ループがバグで赤くなるか、ならないか——曖昧な関門が二値の観測に変わる)

3箇所に書き下された三点セット、1つの概念に1文を費やす description——どれも1語に折り畳める候補。弱いリーディングワード(「徹底的に」)は no-op であり、直すなら別の手法ではなく強い語(「執拗に」)。

## 名前付き失敗モード(診断用)

| 失敗モード | 内容と対処 |
|---|---|
| 早すぎる完了 | 本当に終わる前にステップを閉じる。まず完了基準を鋭くする(安価)。基準がどうしても曖昧で急ぎを観測したときのみ、後続ステップを分割して視界から隠す |
| 重複 | 同じ意味が複数箇所に。単一の真実源に集約し、変更を1箇所編集にする |
| 堆積 | 追加は安全に見え削除は危険に見えるため古い層が沈殿する。刈り込み規律のないスキルの既定の運命 |
| スプロール | 全行が生きていても単に長すぎる。参照をポインタの先に開示し、分岐・順序で分割する |
| no-op | モデルが既定で従う行に負荷だけ払う。テスト: 既定挙動と比べて何かが変わるか?変わらなければ文ごと削除(語を削るのではなく) |
| 否定形 | 禁止による操縦は裏目。肯定形で目標挙動を述べる(前節参照) |

刈り込みは文単位で行う。no-op テストに落ちた文は書き直さず丸ごと消す。

## 書き方の規則(その他)

- **フローチャートは非自明な判断のみ。** 参照資料は表、コードはコードブロック、直線的手順は番号リスト
- **例は優れた1つ。** 完全・実行可能・WHY をコメント・実シナリオ由来。多言語展開や穴埋めテンプレは品質を薄める
- **物語を書かない。**「あのセッションでは〜だった」は再利用不能。技法・パターン・参照として一般化する
- **正規表現や検証で強制できる機械的制約はスキルにせず自動化する。** 文書は判断を要する事柄のために取っておく
- **重い参照(100行超)や再利用ツールのみ別ファイル。** 原則・概念・短いパターンはインライン

## STOP: 1スキルずつ

**スキルを1つ書いたら、次に移る前に必ず停止してテストを完了する。**

- 各スキルを未テストのままバッチで量産しない
- 「まとめた方が効率的」は合理化。未テストのスキル配備は未テストのコード配備と同じ

### テスト省略の合理化テーブル

| 言い訳 | 現実 |
|---|---|
| 「明らかに分かりやすい」 | 自分に明快 ≠ 他エージェントに明快。テストせよ |
| 「ただの参照だから」 | 参照にも欠落や不明瞭がある。検索・適用シナリオでテストせよ |
| 「問題が出たらテストする」 | 問題が出る = エージェントがスキルを使えない。配備前にテストせよ |
| 「自信がある」 | 過信は問題を保証する。テストせよ |

## チェックリスト(各項目を todo 化する)

**RED:** 圧力シナリオ作成(規律系は圧力3種以上を複合)→ スキル無しで実行 → 合理化を逐語記録
**GREEN:** 失敗型を分類し形式を選択 → description はトリガー条件のみ・三人称 → 記録された失敗にちょうど対処する最小スキル → スキル有りで再実行し遵守を確認
**REFACTOR:** 新たな合理化にカウンター追加 → 合理化テーブル・レッドフラグ整備(規律系)→ 防弾になるまで再テスト
**品質:** no-op 文の削除 → 重複の単一真実源化 → リーディングワードへの折り畳み → 200行以内目安
