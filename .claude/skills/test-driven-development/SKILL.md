# テスト駆動開発（TDD）

## 概要

先にテストを書く。失敗を見届ける。通すための最小コードを書く。

**核心原則:** テストの失敗を自分の目で見ていないなら、そのテストが正しいものを検証しているかは分からない。

**字面の違反は精神の違反である。** 言い回しを変えても規律は免除されない。

## 鉄則

```
失敗するテストなしにプロダクションコードを書かない
```

テストより先にコードを書いてしまったら？ **削除してやり直す。**

**例外なし:**
- 「参照用」に残さない
- テストを書きながら「流用」しない
- 見返しもしない
- 削除とは削除である

テストからまっさらに実装し直す。以上。

## 適用範囲

**常に:** 新機能 / バグ修正 / リファクタリング / 挙動変更。

**例外（人間のパートナーに確認）:** 使い捨てプロトタイプ、生成コード、設定ファイル。

「今回だけ TDD を飛ばそう」と思ったら停止。それは合理化である。

## Red-Green-Refactor

### RED — 失敗するテストを書く

あるべき挙動を示す最小のテストを 1 本書く。1 テスト 1 挙動、名前は挙動を語る。

テストの**書き方の詳細**（層の縄張り・モックの線引き・日本語テスト名・古典学派方針）は
`writing-tests` スキルが正である。本スキルが担うのは**順序と規律**のみ。テストを書く段になったら
必ず `writing-tests` に従うこと。

```python
def test_空パターンファイルはExitCode2で拒否する(tmp_path):
    pat = tmp_path / "pat.txt"
    pat.write_text("", encoding="utf-8")
    rc = main(["--patterns", str(pat), str(tmp_path)])
    assert rc == 2
```

### RED の確認 — 失敗を実際に見る

**必須。絶対に飛ばさない。**

```bash
python -m pytest tests/unit/test_cli_args.py -q --tb=line
```

確認事項:
- **失敗**していること（エラーではなく）。ImportError や typo は「赤」ではない
- 失敗メッセージが期待どおりであること
- **機能の欠如**が原因で失敗していること

**いきなり通った？** 既存挙動を検証しているだけ。テストを直す。
**エラーになった？** エラーを直し、正しく「失敗」するまで再実行。

### GREEN — 最小のコード

テストを通す最も単純なコードを書く。テストが要求しない機能・オプション・汎用化は足さない（YAGNI）。

### GREEN の確認 — 成功を実際に見る

**必須。**

```bash
python -m pytest tests/ -q --tb=line
```

- 当該テストが通る
- 他のテストも全部通る
- 出力がクリーン（エラー・**警告ゼロ**）

**通らない？** 直すのはコードであってテストではない。**他が壊れた？** いま直す。

### REFACTOR — 緑になった後だけ

重複除去・命名改善・ヘルパー抽出。テストは緑のまま保つ。挙動は足さない。

### 繰り返す — 垂直スライス（トレーサーバレット）

**1 テスト → 1 実装 → 繰り返し。** テストを全部先に書き溜めてから一括実装する
「水平スライス」は禁止。まとめ書きしたテストは*想像上の*挙動を固定し、実装から学べない。
各サイクルは前サイクルの学びを反映した 1 発の曳光弾であること。

## テスト自体のアンチパターン（サイクル中に常時点検）

- **実装結合テスト** — 内部協調オブジェクトをモックする・プライベートに触れる・裏口（内部状態の直接検査）で検証する。兆候: 挙動が変わっていないのにリファクタで壊れる。
- **トートロジーテスト** — アサーションが期待値を実装と同じ方法で再計算する（`assert normalize(s) == s.strip().lower()` の類）。構造上必ず通り、コードと食い違えない。期待値は**独立した正**（既知の良値リテラル・手計算例・仕様）から取る。
- **水平スライス** — 上記のとおり。垂直スライスで書く。

モック関連の詳細な禁則は [testing-anti-patterns.md](testing-anti-patterns.md) を参照。

## なぜ順序が重要か

- **「後でテストを書いて検証する」** — 後書きテストは即座に通る。即座に通るテストは何も証明しない。テスト先行は「What should this do?」を、後書きは「What does this do?」を答えるだけ。
- **「手動で全ケース確認済み」** — 場当たりは体系ではない。記録が残らず、再実行できない。
- **「X 時間分の削除はもったいない」** — サンクコスト誤謬。信頼できないコードを保持することこそが損失。

## 合理化への反駁テーブル

| 言い訳 | 現実 |
|--------|------|
| 「単純すぎてテスト不要」 | 単純なコードも壊れる。テストは 30 秒で書ける |
| 「後でテストする」 | 即座に通るテストは何も証明しない |
| 「後書きでも目的は同じ」 | 後書き=実装に偏向した検証。先行=仕様の発見 |
| 「手動テスト済み」 | 記録なし・再実行不可。体系ではない |
| 「X 時間分の削除は無駄」 | サンクコスト誤謬。未検証コードは技術的負債 |
| 「参照用に残してテストを先に書く」 | 必ず流用する。それは後書きテスト。削除は削除 |
| 「まず探索したい」 | よい。探索は捨てて TDD で始め直す |
| 「テストしづらい=設計が不明瞭」 | テストの声を聞く。テストしにくい=使いにくい |
| 「TDD は遅い」 | デバッグより速い。実利主義=テスト先行 |
| 「既存コードにテストがない」 | 改善する側になる。既存部分にもテストを足す |

## レッドフラグ — 停止してやり直し

- テストより先にコードがある
- テストが即座に通った
- なぜ失敗したか説明できない
- 「後でテストを足す」「今回だけ」
- 「手動で確認済み」「精神が大事で儀式ではない」
- 「参照として残す」「既存コードを流用」
- 「もう X 時間かけたから削除は無駄」
- 「TDD は教条的、自分は実利的」「今回は特別だから…」

**いずれも意味は一つ: コードを削除し、TDD でやり直す。**

## バグ修正の統合

バグを見つけたら、**まず再現する失敗テストを書く**。その後 TDD サイクルに従う。
テストが修正を証明し、回帰を防ぐ。**再現テストなしにバグを直さない。**
（調査手順は `systematic-debugging`、完了宣言は `verification-before-completion` を参照。）

## 完了前チェックリスト

- [ ] 新規関数・メソッド全てにテストがある
- [ ] 各テストの失敗を実装前に見届けた（原因は機能欠如であって typo ではない）
- [ ] 各テストを通す最小コードのみ書いた
- [ ] `python -m pytest tests/ -q --tb=line` が全緑
- [ ] 出力がクリーン（エラー・警告ゼロ）
- [ ] モックは外部 I/O 境界のみ（`writing-tests` の線引きどおり）

1 つでも欠けたら TDD を飛ばしている。やり直し。

## 最終規則

```
プロダクションコード → 先に失敗したテストが存在する
それ以外 → TDD ではない
```

人間のパートナーの許可なき例外はない。
