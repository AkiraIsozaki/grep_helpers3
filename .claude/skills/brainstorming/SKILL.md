# ブレインストーミング（設計先行ゲート）

<HARD-GATE>
設計を提示し、ユーザーの承認を得るまで、実装スキルの起動・コード作成・雛形生成を一切行わない。
「単純そうだから」は例外にならない。単純に見える作業ほど、暗黙の前提が検証されていない。
</HARD-GATE>

## チェックリスト（各項目を todo 化して消化する）

1. **文脈探索**: 関連する既存コード・`docs/` の設計文書・過去の `.steering/` を読み、現状を把握する
2. **質問は1メッセージ1問**: 複数の質問を並べない。回答を得てから次の質問へ進む
3. **選択肢の提示**: アプローチを2〜3案、トレードオフ付きで提示し、推奨案を明示する
4. **設計のセクション毎承認**: 設計をセクションに分けて提示し、セクション毎に承認を得る
5. **設計文書の作成**: 承認された設計を `steering` スキル（計画モード）で `.steering/YYYYMMDD-<トピック>/` の requirements.md・design.md に落とす
6. **自己レビュー**: プレースホルダ残存・内部矛盾・スコープ逸脱・曖昧語を走査して修正する
7. **ユーザーによる文書レビュー**: 書き上がった設計文書そのものを確認してもらう
8. **ハンドオフ**: `steering` の計画モードで tasklist.md を作成する。**終端状態はこれのみ**（設計承認から直接実装へ飛ばない）

## 設計原則

- **YAGNI を徹底する**: 今必要なものだけを設計する。「将来のために」は削る
- **分離と明確なインターフェース**: 小さく焦点の定まった構成単位に分ける
- **既存パターンに従う**: 既存コードベースでは、新奇な構造より現行の構造規約（`coding-conventions` 参照）に合わせる
- **無関係なリファクタリングを混ぜない**: 気づいた改善は記録して別作業にする（`refactoring` スキルの縄張り）

## スコープガード

要求が複数の独立したサブシステムに跨る場合は、先にサブプロジェクトへ分解する。
各サブプロジェクトが自分の 設計 → 計画 → 実装 のサイクルを持つ。

## アンチパターン

| 合理化 | 実際 |
|---|---|
| 「単純すぎて設計は不要」 | 単純な変更こそ前提の食い違いが露見しない。ゲートは規模で免除されない |
| 「口頭で合意したから文書は省略」 | 文書化されない合意はコンパクション（文脈圧縮）で消える |
| 「実装しながら設計を固める」 | それはプロトタイプ。捨てる前提で明示的に行い、本実装は設計承認後に始める |
| 「質問をまとめて聞いた方が効率的」 | 複数質問は回答の質を下げる。1問ずつが結果的に速い |
