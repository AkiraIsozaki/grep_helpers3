# プロジェクト文書セットアップ

docs/ideas/ 配下の構想メモを起点に、プロジェクトの設計文書一式を順に作成する。引数: $ARGUMENTS（特定の構想ファイルを指定できる。未指定なら docs/ideas/*.md 全部を対象とする）。

## 前提

- 対象プロジェクトは Python 3.12 の CLI ツール `grep_analyzer`。テストは pytest のみ（`python -m pytest tests/ -q --tb=line`）。
- 実装規約に関する文書は**作成しない**。実装規約は `coding-conventions` / `writing-tests` スキルが既に正として存在するため、それらと重複・矛盾する文書を新たに書かないこと。

## 手順

### ステップ 0: 構想の読み込み

docs/ideas/*.md（または $ARGUMENTS で指定されたファイル）を全て読み、プロジェクトの目的・課題・要望を把握する。docs/ideas/ が存在しない、または空の場合はその旨を報告して終了する。

### ステップ 1: PRD（人間承認ゲートあり）

`prd-writing` スキルを起動し、構想メモを元に PRD を作成する。

**PRD 完成後は必ず停止し、ユーザーの承認を待つこと。** 承認されるまでステップ 2 以降へ進んではならない。指摘があれば PRD を修正し、再度承認を求める。

### ステップ 2: 機能設計書（以降は自動）

承認された PRD を入力として `functional-design` スキルを起動し、機能設計書を作成する。ここから先は人間の承認を待たず自動で進めてよい。

### ステップ 3: アーキテクチャ設計書

`architecture-design` スキルを起動し、機能設計書と整合するアーキテクチャ設計書を作成する。

### ステップ 4: リポジトリ構造定義書

`repository-structure` スキルを起動し、リポジトリ構造定義書を作成する。

### ステップ 5: 用語集

`glossary-creation` スキルを起動し、ここまでの文書に登場する用語を整理した用語集を作成する。

> 注記: 旧手順にあった「開発ガイドライン作成」ステップは廃止した。実装規約は `coding-conventions` / `writing-tests` スキルが既に正として存在する。

## スキップ規則

各ステップの開始時に docs/ 配下に該当文書が既に存在するか確認し、**存在する場合はそのステップをスキップして「既存のためスキップ」と報告する**（上書きしない）。既存文書の更新が必要な場合は、その旨を最終報告に含めてユーザーの判断を仰ぐ。

## 完了報告

全ステップ終了後、以下を報告する。

- 作成した文書のパス一覧
- スキップした文書とその理由
- 文書間で発見した矛盾・未解決事項（あれば）
