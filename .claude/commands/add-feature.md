# 機能追加

以下の機能を grep_analyzer に追加する: $ARGUMENTS

8 ステップのループで進める。**ステップ 1 の設計承認がゲートであり、承認後の実装フェーズ（ステップ 2〜8）はユーザーへ質問せず自律で完遂する。** 実装フェーズで判断に迷ったら、承認済み設計と既存コードのパターンに最も忠実な選択肢を採り、判断内容を最終報告に記録する。

## ステップ 1: 設計（承認ゲート）

`brainstorming` スキルを起動し、要求の意図・要件・設計を探索する。スキルの設計承認ゲートを尊重し、**ユーザーが設計を承認するまで実装に着手しない。**

## ステップ 2: プロジェクト文脈の読み込み

CLAUDE.md と docs/ 配下の設計文書（PRD・機能設計書・アーキテクチャ設計書・リポジトリ構造定義書・用語集）を読み、承認済み設計との整合を確認する。

## ステップ 3: 既存パターンの調査

src/ と tests/ を grep し、類似機能の実装パターン・命名・テスト構成を把握する。新規コードは既存パターンに揃える。

## ステップ 4: 作業計画

`steering` スキルを起動し、計画モードで作業計画とタスクリストを文書化する。タスクは 1 つずつ独立に完了検証できる粒度に分割する。

## ステップ 5: タスクリスト消化ループ

タスクリストを先頭から 1 タスクずつ消化する。各タスクで:

1. `test-driven-development` スキルを遵守する（Red → Green → Refactor。実装より先にテストを書く）
2. `coding-conventions` / `writing-tests` スキルの規約に従う
3. タスク完了ごとに `python -m pytest tests/ -q --tb=line` を実行し、全テスト成功を確認してから次のタスクへ進む

## ステップ 6: 実装検証

Agent ツールで subagent_type: implementation-validator を起動し、実装が承認済み設計とタスクリストを満たしているか検証させる。指摘があれば修正し、再検証する。

## ステップ 7: 全テスト実行

`python -m pytest tests/ -q --tb=line` を実行し、全テストが成功することを確認する。失敗があれば `systematic-debugging` スキルを起動して修正する。

## ステップ 8: 振り返りと文書更新

`steering` スキルで振り返りを記録する。実装により docs/ の設計文書・用語集に差分が生じていれば更新する。

## 完了条件

最後に `verification-before-completion` スキルを起動し、完了主張の前に全証跡（テスト結果・検証結果・文書更新）を確認してから完了を報告する。報告には、実装フェーズで自律的に下した判断の一覧を含める。
